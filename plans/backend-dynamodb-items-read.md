# Backend DynamoDB Read for `GET /api/items`

## Context

`docs/state.md` lists the following item as **In Progress**:

> Backend access to DynamoDB
> - Read from DynamoDB and return its contents in the response
> - Scope: `/api/items` only
> - Expected result: empty

Today, `apps/backend/src/app.ts` returns a hard-coded `dummyItems` array
in response to `GET /api/items`. The CDK `DataStack` already provisions
the items table (`itemsTable`, partition key `userId`, sort key `itemId`,
on-demand billing), and `BackendStack` already wires the table name into
the Lambda runtime as the `TABLE_NAME` environment variable.
`BackendDataAccessStack` already grants the Lambda role
`Query` / `GetItem` / `PutItem` / `UpdateItem` / `DeleteItem` /
`BatchWriteItem` against the table and its indexes.

The HTTP API in `BackendApiStack` is fronted by an `HttpJwtAuthorizer`
bound to the Cognito user pool, so by the time a request reaches the
Lambda the JWT has been validated and the `sub` claim (the Cognito user
identifier) is available on `event.requestContext.authorizer.jwt.claims`.

The objective is to replace the dummy data with a real DynamoDB
`Query` keyed by the caller's `userId`, returning whatever items exist
for that user. The table is currently empty, so the expected result is
`{ "items": [] }`. No write path, no auth bypass, no schema migrations.

## Decisions

| Decision | Choice |
|---|---|
| AWS SDK | v3 — `@aws-sdk/client-dynamodb` + `@aws-sdk/lib-dynamodb` (DocumentClient) |
| Where the SDK lives | `apps/backend` `dependencies` (bundled by `NodejsFunction` esbuild, tree-shaken by `minify: true`) |
| User scoping | `userId = event.requestContext.authorizer.jwt.claims.sub` from the validated JWT |
| Read shape | `Query` on `userId` partition key (sort by `itemId` is the natural order returned) |
| Sort by purchase date | Done in memory after `Query` (descending: newest first). Acceptable while item counts per user are small; revisit with a GSI when needed |
| DynamoDB attribute names | Match the response shape: `userId`, `itemId`, `name`, `purchaseYear`, `purchaseMonth`. Disposal/price attributes are not yet stored or returned (out of scope for this step) |
| DynamoDB client lifetime | One module-level `DynamoDBDocumentClient` instance reused across Lambda invocations (warm-start friendly) |
| Region | Implicit — let the SDK resolve from the Lambda execution environment (`AWS_REGION`) |
| Local dev (`apps/backend/src/dev.ts`) | Out of scope. The "Backend feature tests running locally against a local DynamoDB" item in `state.md` is explicitly **Planned (not yet started)**; we will not pre-empt it here. `dev.ts` will keep working for the `/` route only, and `GET /api/items` against `dev.ts` will fail fast on the missing JWT — that is acceptable for now |
| Error handling | Trust the JWT authorizer guarantees the claim exists in the deployed path; on the off chance it doesn't, return `401`. DynamoDB errors propagate as a `500` (Hono default) — no custom catch |

## Implementation details

### 1. `apps/backend/src/items-repository.ts` (new)

- Import `DynamoDBClient` from `@aws-sdk/client-dynamodb`,
  `DynamoDBDocumentClient` and `QueryCommand` from `@aws-sdk/lib-dynamodb`.
- Construct a single module-level `DynamoDBDocumentClient.from(new DynamoDBClient({}))`
  so warm Lambda invocations reuse the connection.
- Read `process.env.TABLE_NAME` once, throw at module load if missing —
  this is a misconfiguration, not a runtime error.
- Export an `Item` type matching the response shape
  (`itemId`, `name`, `purchaseYear`, `purchaseMonth`).
- Export `async function listItemsByUser(userId: string): Promise<Item[]>`:
  - `QueryCommand` with `KeyConditionExpression: "userId = :u"`,
    `ExpressionAttributeValues: { ":u": userId }`.
  - Map each returned attribute map to the `Item` shape, defensively
    coercing `purchaseYear`/`purchaseMonth` to `Number` so a DynamoDB
    string-typed value doesn't silently corrupt the response.
  - Items missing required attributes are skipped (defensive — the table
    is empty today, so this codepath is unreachable in this step, but
    the guard keeps the response shape honest once writes land).

### 2. `apps/backend/src/app.ts` (modify)

- Remove the `Item` type and `dummyItems` array.
- Import `listItemsByUser` and `type Item` from `./items-repository.js`.
- Import `LambdaEvent` from `hono/aws-lambda` for typing `c.env.event`.
- Replace the `app.get("/api/items", ...)` body with:
  - Pull the JWT claims from
    `(c.env.event as LambdaEvent).requestContext.authorizer?.jwt?.claims`.
    HTTP API v2's authorizer object lives on `requestContext.authorizer.jwt.claims`.
  - If no `sub` claim, return `c.json({ message: "Unauthorized" }, 401)`.
    (The JWT authorizer already enforces this in deployed traffic; the
    check is a tripwire for misconfiguration, not a real auth gate.)
  - `const items = await listItemsByUser(sub);`
  - Sort descending by `(purchaseYear, purchaseMonth)`:

    ```ts
    items.sort((a, b) =>
      b.purchaseYear !== a.purchaseYear
        ? b.purchaseYear - a.purchaseYear
        : b.purchaseMonth - a.purchaseMonth,
    );
    ```

  - Return `c.json({ items })`.

### 3. Bundling considerations

- `BackendStack`'s `NodejsFunction` already runs esbuild with
  `format: ESM`, `minify: true`, `target: node22`,
  `mainFields: ["module", "main"]`, and the require-shim banner.
- AWS SDK v3 ships ESM and tree-shakes well; only `QueryCommand` and the
  `DocumentClient` marshalling code will be retained.
- No bundling-config change is needed. We do **not** mark
  `@aws-sdk/*` as external (Lambda's runtime bundles SDK v3 as well, but
  the version drifts with runtime upgrades; bundling our own pinned copy
  keeps build output reproducible).

## Verification plan

After deploying with `cdk deploy --all --require-approval never`:

1. From the deployed SPA (signed in via Google), navigate to `/items`.
   The page should render with the empty state — no rows, no error.
2. Inspect the network tab: `GET /api/items` should return
   `200` with body `{ "items": [] }`.
3. CloudWatch Logs for the Lambda should show no errors and a single
   `Query` call per request (visible only if a debug log is added —
   not required).
4. As a sanity check that the auth path is intact, call
   `GET /api/items` without an `Authorization` header from `curl`:
   the API Gateway JWT authorizer must reject with `401` before the
   Lambda is ever invoked.
5. (Optional) Insert one row by hand via the AWS console with
   `userId = <your Cognito sub>`, refresh `/items`, and confirm the
   row appears. Remove the row when done — write paths are not part
   of this step.

## Out of scope

- POST/PUT/DELETE handlers for `/api/items` (separate state.md item).
- Pagination (the spec calls for it but the frontend's pagination UI is
  already inert and the table is empty; defer with `LastEvaluatedKey`
  support when row counts justify it).
- Disposal date / purchase price attributes (not yet in the response
  contract, not yet in the frontend).
- A GSI for purchase-date sort.
- Local-DynamoDB feature tests (explicitly Planned, not yet started).
- `apps/backend/src/dev.ts` parity with the deployed JWT path.
