# Plan: Provision DynamoDB Table for Items (In Progress item in docs/state.md)

## Context

`docs/state.md` lists two "In Progress" tasks:

- DynamoDB resource design and provisioning
- Add the DynamoDB definition to the CDK under `infra/cdk`

These are both parts of the same unit of work: adding the data-store layer so the backend Lambda stack (next "Planned" item) can read and write items. The backend is not yet implemented — the Lambda stack plans to "return an empty item list" as its first step — so DynamoDB only needs the table itself. Associations (IAM grants to Lambda) will come with the Lambda stack later and are explicitly out of scope here, consistent with the "separate creation from association" policy recorded in memory.

`docs/spec.md` also classifies DynamoDB explicitly under the "change rarely, caution when modified" CDK stack tier, so the table should live in its own stack (not bundled into the existing `Storage` stack, which is for S3 website hosting).

## Design Decisions

### Entity model (from `docs/spec.md` §Entities)

Item attributes:
- Item name
- Purchase date (year + month)
- Purchase price
- Disposal date (year + month, optional)

The app is multi-user via Cognito (`docs/spec.md` §Authentication Strategy). The backend will extract `sub` from the validated Cognito JWT and scope all item queries by user.

### Table schema

| Field | Type | Role |
|---|---|---|
| `userId` | string (S) | Partition key — Cognito `sub` |
| `itemId` | string (S) | Sort key — generated by backend (ULID/UUID) |

Non-key attributes (schemaless, stored per item, not modeled in CDK):
- `itemName` (string)
- `purchasePrice` (number, JPY)
- `purchaseYearMonth` (string, `YYYY-MM`)
- `disposalYearMonth` (string, `YYYY-MM`, optional)

### Why no GSI now

`docs/spec.md` requires the item list page to be "sorted by purchase date in descending order (newest first)". A strict read would ask for a GSI on `userId` + `purchaseYearMonth`. Skipping it initially because:

- The app is explicitly personal-use (`docs/intent.md`), so per-user item count is small (tens to low hundreds). A single Query by `userId` returns all items in one or two pages; backend-side sort is adequate.
- A GSI costs additional write units and storage. The "$0 when unused" intent (`docs/intent.md`) is preserved regardless (on-demand billing), but the simplicity win matters for a learning project.
- If this becomes a real bottleneck, a GSI can be added later as a table update. The write pattern (`purchaseYearMonth` is a plain attribute, not embedded in the SK) keeps that migration easy — the SK is a stable itemId, so purchase-date edits don't require delete+recreate.

### Other table settings

- **Billing mode**: `PAY_PER_REQUEST` — satisfies the "$0 in any unused month" requirement (`docs/intent.md`).
- **Removal policy**: `DESTROY` — matches `StorageStack` and `AuthStack` so developers can freely recreate their per-developer environment (`docs/spec.md` §Development Environment).
- **Encryption**: AWS-managed default (no extra setting needed).
- **Point-in-time recovery / streams / TTL**: not enabled. None are required by the current feature set.
- **Physical table name**: not set (let CDK auto-generate, matching the existing `WebsiteBucket` pattern).

### Stack placement

New stack `DataStack`, instantiated as `${envName}-Data`:

- Follows the existing single-file-per-stack convention (`infra/cdk/src/stacks/*.ts`).
- Exposes the table as a `public readonly itemsTable: dynamodb.TableV2` property so the future Lambda stack can receive it via constructor props and call `itemsTable.grantReadWriteData(fn)` — this is the "association" step that belongs in the backend stack, not here.
- Uses `TableV2` (the warm-started L2 construct introduced in modern CDK) — cleaner than `Table` and the preferred default in CDK v2 today.

No changes to existing stacks. `DataStack` has no dependencies on Storage, Distribution, Deployment, or Auth, and nothing yet depends on `DataStack` — the wire-up will happen when the Lambda stack lands.

## Files to Modify

### Create: `infra/cdk/src/stacks/data-stack.ts`

New stack file following the pattern in `infra/cdk/src/stacks/storage-stack.ts`:

- Import `Stack`, `StackProps`, `RemovalPolicy`, `CfnOutput` from `aws-cdk-lib`.
- Import `aws-cdk-lib/aws-dynamodb` as `dynamodb`.
- Export class `DataStack extends Stack` with `public readonly itemsTable: dynamodb.TableV2`.
- Create the table with:
  - construct id: `"ItemsTable"`
  - `partitionKey: { name: "userId", type: dynamodb.AttributeType.STRING }`
  - `sortKey: { name: "itemId", type: dynamodb.AttributeType.STRING }`
  - `billing: dynamodb.Billing.onDemand()`
  - `removalPolicy: RemovalPolicy.DESTROY`
- Emit a `CfnOutput` `ItemsTableName` with `this.itemsTable.tableName`, mirroring the `BucketName` output in `StorageStack`.

### Modify: `infra/cdk/src/main.ts`

Add one import and one stack instantiation alongside the existing ones:

```ts
import { DataStack } from "./stacks/data-stack";
// ...
new DataStack(app, `${envName}-Data`);
```

Placement: after the `AuthStack` instantiation (order doesn't matter — no dependencies — but keeping Data last reads naturally: web, then auth, then data).

### Modify: `docs/state.md`

Move both "DynamoDB resource design and provisioning" and "Add the DynamoDB definition to the CDK under `infra/cdk`" from "In Progress" to "Completed". Keep the rest of the file unchanged.

## Reused Existing Patterns

- Stack prefixing with `envName` context — `infra/cdk/src/main.ts:9` (`app.node.tryGetContext("envName") ?? "dev"`).
- `public readonly <resource>` exposure for cross-stack consumption — `infra/cdk/src/stacks/storage-stack.ts:6`, `infra/cdk/src/stacks/auth-stack.ts:18-19`.
- `RemovalPolicy.DESTROY` for dev-friendly teardown — `infra/cdk/src/stacks/storage-stack.ts:13`, `infra/cdk/src/stacks/auth-stack.ts:35`.
- `CfnOutput` for key resource identifiers — `infra/cdk/src/stacks/storage-stack.ts:17-19`, `infra/cdk/src/stacks/auth-stack.ts:87-97`.

No new constructs, helpers, or shared modules are introduced.

## Verification

The user will run `cdk deploy` themselves. Before handing off, do the following from `infra/cdk/`:

1. **Type check**: `pnpm exec tsc --noEmit` (or equivalent) — ensures the new stack file and `main.ts` wiring compile.
2. **Synthesize**: `pnpm cdk synth dev-Data` — confirms the CloudFormation template renders and contains:
   - One `AWS::DynamoDB::GlobalTable` (TableV2) resource.
   - `KeySchema` with `HASH=userId`, `RANGE=itemId`.
   - `BillingMode: PAY_PER_REQUEST`.
   - `DeletionPolicy: Delete` on the table.
   - Outputs section containing `ItemsTableName`.
3. **No-op check on existing stacks**: `pnpm cdk diff dev-Storage dev-Distribution dev-Deployment dev-Auth` should report no changes, since this plan does not touch their wiring.

Deferred to the user (as requested):
- `pnpm cdk deploy dev-Data` to provision the table in AWS.
- Post-deploy sanity check: `aws dynamodb describe-table --table-name <name from output>` to confirm the schema in the live account.
